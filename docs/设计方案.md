# 设计方案

> 配套 [变更记录.md](变更记录.md)（记录改了什么）。本文记录每个非纯迁移改动的**方案与理由**。

## §1 T6 — screens/base.py 用旧实现替换骨架占位草稿
**背景**：新项目 screens/base.py 在骨架阶段写了一份「设计草稿」——用 Any 类型占位、screen/priority/has_anchor 用 @property、parse(observation, region_reader)/decide(state, observation) 签名、无 DelegatingScreenHandler。其 Protocol 签名与旧项目经测试的实现不一致。
**方案**：以旧 base.py 实现（ScreenHandler Protocol：has_anchor(anchors)->(bool,float) / parse(region_texts,profile,image) / decide(observation,state,policy) + DelegatingScreenHandler）替换占位草稿。顶部 docstring 改中文并补「decide 接收 policy 是有意的，不是泄漏」说明。
**理由**：
- PRD T6 明确「DelegatingScreenHandler 迁移过渡，行为 1:1 零回归」。
- docs/新项目技术设计.md §6.2 的 Protocol 签名与旧版一致。
- 旧实现经 148 测试 + 实跑迭代验证；占位草稿未经测试。
- 保留占位草稿签名会造成文档与代码矛盾，且后续 classifier(T8)/policy(T12)/live_loop(T16) 都按旧签名调用。

## §2 T7 — rebuild_anchor_handlers 新增 + 原地替换
**背景**：旧 screens/__init__.py 模块加载时一次性构建 HANDLERS + ANCHOR_HANDLERS（sorted 一次）。新项目分阶段迁移：T7 先建空框架，handler 实例在 T8/T10/T13 后逐步注册。
**方案**：
- 新增 `rebuild_anchor_handlers()`：handler 注册/更新后调用，按 priority 升序重排 ANCHOR_HANDLERS（仅含 anchor_fn 的 handler）。
- rebuild 用 `ANCHOR_HANDLERS[:] = sorted(...)`（原地替换内容），非 reassign。
**理由**：
- 分阶段迁移需可重复调用的 rebuild（旧版一次 sorted 不适用）。
- 原地替换保持对象身份：`from screens import ANCHOR_HANDLERS` 的引用在 rebuild 后仍指向同一（已更新）对象；reassign 会断开引用（Python `from import` 拿到的是当时绑定的对象，之后模块级名字 reassign 不更新它）。该陷阱由 test_screens_registry 复现并修复。
- HANDLERS.clear() 已是原地操作，ANCHOR_HANDLERS 原地替换保持两者一致。

## §3 中文 \uXXXX 转义 → 直接字符
**背景**：旧项目 fixtures / text_constants 等用 \uXXXX 转义存中文（疑为规避历史编码问题）。
**方案**：改为直接中文字符。
**理由**：新项目全 UTF-8（logging_setup 强制 UTF-8 控制台/文件输出）；直接中文更可读、可 grep 检索，与项目中文文档/注释风格一致；Python 源码中 \uXXXX 与直接字符语义完全等价。

## §4 单元测试新增与重组
**背景**：旧测试按旧模块组织——test_regions_and_vision 混合 regions+vision；无专门 screens/text_utils/ocr_reader 测试。
**方案**：按新项目拆分后的模块对应组织测试；为新增框架代码补测试。
**理由**：
- 模块对应测试（单一职责）符合拆分后结构，定位精准。

- NoopOcrEngine / _FakePyAutoGui 注入让管线/执行测试无需 GPU/真实鼠标。

## §5 T12/T13 — policy.py 拆分 + Mixin 模式
**背景**：旧 policy.py 828 行（超 400 规范），含 PolicyConfig + event_db + TrainerPolicy（所有 decide_X 方法）。旧 decide 已通过 `screens.HANDLERS` 分发：handler.decide 调用 policy.decide_X。
**方案**：
- `policy/config.py`：PolicyConfig（阈值/坐标集中）。
- `policy/event_db.py`：事件库 + events.json 加载 + 字符级模糊匹配（阈值 0.6）。
- `policy/engine.py`：TrainerPolicy 核心（__init__/_pending_X 状态/decide 分发/training_score/_reset_character_scroll）。
- `policy/<name>.py`：7 个决策 Mixin（decide_X + 专属 helper），TrainerPolicy 多继承它们。
**理由**：
- 满足单文件 ≤400 行规范（policy.py 828 → 各文件 <250）。
- Mixin 保持 decide_X 用 `self.config`/`self._pending_X`，无需把方法签名改成函数并传 policy 实例 —— decide_X 仍是 TrainerPolicy 的方法（来自 Mixin），handler.decide 调用 `policy.decide_X` 不变。
- decide 已分发到 handler.decide（注册表架构），本拆分只动 policy 内部组织，不改分发契约。
- 非纯迁移（单类→多 Mixin 是结构性重构），但 decide_X 逻辑逐字不变（坑 #12/#13/#15/#16 防翻转/双向滚动原样保留）。

## §6 T8 — classifier 拆分 + handler 注册（policy 闭环）
**背景**：旧 classifier.py 784 行（超 400），含分类器 + anchor 常量 + 14 消歧 signature + 密度 helper。旧 screens/__init__.py HANDLERS 注册 DelegatingScreenHandler（转发 parse/decide/has_anchor），但 T7 时是空骨架。
**方案**：
- `classifier.py` 核心：classify_by_ocr（两遍加速：fast anchors→全量）/ classify_by_blue_button / classify_hybrid（实跑默认，OCR+蓝键+视觉三层 fallback）。
- `classifier_anchors.py`：ANCHOR_REGIONS_BY_SCREEN/ANCHOR_TEXT_BY_SCREEN + _read_anchor_regions + _match_screen（先走 ANCHOR_HANDLERS 注册表签名，再 fallback anchor 评分）+ classify_by_filename（离线）。
- `classifier_signatures.py`：14 个 _has_X_signature（坑 A 类 1-11 消歧）+ 视觉密度 helper（journey origin 组：角色选择/祝福装备/旅程起点 按内容密度区分，坑 #1/#11）。
- `screens/__init__.py`：21 DelegatingScreenHandler（_decide_X 薄包装校验 payload + 调 policy.decide_X），模块加载时 rebuild_anchor_handlers() 构建 ANCHOR_HANDLERS。
**理由**：
- 满足 ≤400 行规范（784 → 三文件各 <300）。
- 分类逻辑 1:1（classify_hybrid 三层 fallback + 14 signature 消歧 + 陷阱画面 priority=2 早检查全部原样）。
- handler 注册是注册表架构闭环：整合 parse(T10)+decide(T13)+has_anchor(T8)，policy.decide 现能闭环分发（验证：REWARD→click continue、INITIAL→click start），消除 T13 后 decide→空 HANDLERS→pause 的 gap。
- classifier 拆分是结构性重构（非纯迁移），但分类逻辑逐字不变。

## §10 OCR 引擎替换：PaddleOCR → RapidOCR（ONNX Runtime GPU）
**背景**：T17 后实机验证大厅帧，发现 OCR 全乱码（paddleocr 2.7.3 对游戏 UI 幻觉 194 行随机汉字），分类被乱码掷骰子误导（大厅误判 post_training 1.00）。诊断闭环：①坐标新旧逐字节相同（排除迁移坐标问题）；②旧项目同样 pin paddleocr==2.7.3 + paddlepaddle-gpu==3.0.0b2；③ocr.py 代码按 paddleocr **3.x** 写的（PP-OCRv4_mobile 参数 + 处理 3.5/3.x 输出），requirements 的 ==2.7.3 是陈旧 pin。坑 #37（真 OCR 准确率）从未验证（旧 148 测试用 NoopOcrEngine）。
**方案**（用户授权优化 + 要稳定 GPU OCR）：换 RapidOCR（rapidocr-onnxruntime）——同款 PP-OCRv4 模型但走 ONNX Runtime，彻底摆脱 paddlepaddle 版本地狱。
- ocr.py：`PaddleOcrEngine` → `RapidOcrEngine`（__init__ use_cuda=True 构造 `RapidOCR(det/cls/rec_use_cuda=True)`，GPU 失败回退 CPU；rapidocr 缺则 raise RuntimeError 让 `_create_ocr` 回退 noop）。read_text/read_lines 走 RapidOCR 输出 `[box,text,score]` → OcrResult/OcrLine（box 4 点转 axis-aligned bbox）。
- 调用点跟改（runtime/read_regions/live_loop/test/process_manager）；`--use-paddle` flag 名保留（web UI 在用，改名扩爆炸半径），实际走 RapidOCR。
- requirements：paddleocr + paddlepaddle-gpu → rapidocr-onnxruntime + onnxruntime-gpu；环境清理卸载 paddleocr/paddlex/paddlepaddle-gpu（code 无 import paddle）。
**理由**：
- 根因是 OCR 引擎/版本栈，非坐标/锚点/迁移（三者皆证据排除）。paddleocr 2.7.3 用旧默认模型（3.x 参数被 `**kwargs` 吞）→ 在本游戏字体幻觉；3.x 又依赖 paddlex 的 PaddleStaticRunner 走 PIR，撞 paddlepaddle-gpu 3.0.0b2 beta 未完成的 PIR 算子崩溃。RapidOCR 用相同 PP-OCRv4 但 ONNX Runtime（工业级稳定 + CUDAExecutionProvider GPU），同时消灭两个失败模式。
- 实机闭环：大厅帧 RapidOCR 读出全部正确文字 → 分类 post_training(1.00,误)→training_hub(0.83,对) → 决策点训练按钮（正确）。
- 坐标（坑 #34）顺带洗清：本就是旧项目 battle-tested 值（新旧逐字节相同），无需重新校准；坐标误背的锅回到 OCR 引擎。
- 非纯迁移（OCR 引擎替换 + 依赖栈变更），但 OCR 接口契约（OcrEngine Protocol：read_text/read_lines）不变，调用方零感知；NoopOcrEngine 驱动的 131 测试不受影响。

## §11 训练人头计数 count_heads（模板匹配法）
**背景**：早期游戏（前 N 回合可配置）选"人头最多"的训练以最大化支援卡羁绊。支援卡头像 = **固定角色**（阵容固定，每回合只是分配到不同训练），故可按头像内容做模板匹配。其中 2 个为"不作数"头像（不给羁绊），不计入。游戏在"选中某训练"后于面板显示该训练当前人头（位置每回合变，可延伸到卡片区）。
**方案**（演进：std/edge → 模板匹配）：
- 先试 std/edge 法（局部方差+Canny 边缘，0/1 在场）：单头像帧(1,1,1,0,0)对，但遇同卡多头(guts=2)封顶 1、不作数头需特殊处理、宽区域 blob 计数混卡片 UI 噪声——不鲁棒，弃。
- 改**模板匹配**：每个作数头像存 `config/assets/counting_head_*.png`；`count_heads(image, search_region=None)` 对每个模板 matchTemplate（默认**全图**搜——人头位置每回合变且延伸到卡片区，限小区域会把头切边漏匹配），得分 > 0.85 即该头在场，数命中数。不作数头像(non_counting_head_*.png)不在计数集，自动排除。
- 模板来源：用户裁 / 自行从截图裁（新支援卡）。实机提取 wisdom 头：用已知模板(c2)结构定位 peak → 裁该位置 → 存模板。
**理由**：
- 模板匹配按头像**内容**精确识别（命中 0.96-1.0 vs 非命中 <0.78，阈值 0.85 干净分离），不怕位置变/同卡多头/暗头像。作数/不作数区分天然（不在计数集即排除），正是用户提出的"存不作数模板、匹配到就排除"思路的落地（进一步直接按作数模板计数）。
- 全图搜 vs 限区：限区把延伸到卡片区的人头（guts 第二个头 y≈368）切边致漏匹配（crop 到 390，头到 486），全图避免；模板独特性保证不误匹配卡片 UI。
- 实机验证两套真值：(1,1,1,0,0) 与 (0,0,2,1,0) 全对。
- 局限：模板集需覆盖阵容所有作数头（缺则漏数，往 config/assets/ 加 counting_head_*.png 即可）；inspector 早期游戏接入（点 5 卡读人头选最多）为后续。非纯迁移（新功能）。

## §12 早期游戏训练决策 + 住处休息回心情
**背景**：用户策略——早期游戏（前 N=20 回合可配置）攒支援卡羁绊（选人头最多的训练）；全<=1 时无人头值得选，去住处花 30 块休息回心情（mood NORMAL→GOOD→BEST，越高训练属性越高），钱不够则露宿。
**方案**：
- `TrainingInspector` 加早期游戏分支（`decide` 多 `image`+`policy` 参数；`current_round <= EARLY_GAME_HEAD_ROUNDS`）：逐张点 5 卡，每点一张后下帧 `count_heads(image)` 读其人头记 `head_counts`；读全 → `decide_early_training`。
- `decide_early_training(head_counts)`：max<=1 → None(休息)；否则选 max（平局按 力量>体力>韧性>专注>保护）。
- 全<=1（休息）：inspector 置 `policy._needs_rest` + `_rest_for_mood` + 点 `back_button` 回大厅 → 大厅 `_decide_training_hub` 消费 `_needs_rest` 点休息 → `decide_rest` 见 `_rest_for_mood` 选住处(30, mood)；钱<30 → 露宿。标志在 decide_rest 确认后清。
- 非早期回合：保留原 stat_gain 决策（max 增益，3 卡 inspect）。
**理由**：
- 早期攒羁绊（人头多=多支援卡加成）+ 心情高=训练属性高，是养成前期最优。
- 全<=1 休息回心情而非硬训练（没好头时心情收益 > 强行训练）。
- 住处(30,心情) vs 冥想室(60,体力)：`_rest_for_mood` 标志区分两种休息目的；早期回心情用住处正是用户指定。
- 决策与检测解耦：`decide_early_training` 纯函数（易测），inspector 负责点击+读数状态机。
- 实机验证当前帧 (0,0,2,1,0) → 选 guts ✓；全<=1 → 触发住处休息链。
- 非纯迁移（旧项目无此功能）。

## §13 OCR 批量化提速（17 倍，满足单轮 ≤30s）
**背景**：实跑发现 `classify_hybrid` 一次 ~40s（`_read_anchor_regions` 对 ~40 个 anchor 区域逐次 `crop_region + read_text`，GPU 下每次 ~1s），一轮训练 ~5 分钟——不可用。用户要求一轮训练 ≤30s。
**诊断**：RapidOCR 全图 `read_lines` 只需 1.9s（GPU），一次拿到全部 text+bbox。瓶颈不是引擎，是"逐区域单独 OCR"的调用次数。classify 的 fast+full 两遍 + parse 各做一次 read_lines → 3 次/帧，合计 ~5-6s。最关键：从"每区域一次 OCR"→"全图一次 + bbox 匹配"即可降 1-2 个量级。
**方案**：
- `classifier_anchors._read_anchor_regions`：从 `ocr.read_text(crop_region(...))` 逐区域 → 接 `RegionOcrReader.read_names`（走 reader 的全图 read_lines 缓存 + bbox 中心点匹配）。anchor 仅需命名的区域 text，`read_names` 一次全图 OCR 后按 region rect 匹配返回——classify 两遍共 1 次 read_lines。
- `RegionOcrReader` 批量化：加 `self._lines` 全图 OCR 缓存（首次 `read_*` 触发 `self.ocr.read_lines(image)` 填；同一 reader 同一帧各 `read_*` 共享）。`read_where` 改为按 region rect 中心点匹配 OCR 行的 bbox（`_line_center_in_rect`），text 拼接、confidence 取均值。保留 `read_names/read_prefixes/read_all/read_ocr_regions` 全走 `read_where`。
- classify + parse 共享 reader：`classify_hybrid`/`classify_by_ocr` 参数 `ocr_or_reader`（`isinstance(..., RegionOcrReader)` 兼容旧 `ocr` 参数，测试不破）；`live_loop` 提前创建 `reader`，分类和 payload 读取共用——parse 复用 classify 的全图 read_lines 缓存（≈0s）。
- GPU 修复：onnxruntime-gpu 1.27 需 cuDNN 9 + CUDA 13，系统 CUDA 13.3 ✓ 但缺 cuDNN → `pip install nvidia-cudnn-cu13`(cuDNN 9.23)、`nvidia-cublas-cu13`；`ocr.py` 模块级 PATH 注入（`os.environ["PATH"]` 加 `site-packages/nvidia/*/bin`），让 onnxruntime 的 `CUDAExecutionProvider` 能加载 cuDNN DLL（原来缺→CPU fallback→慢 3 倍）。
**理由**：
- 瓶颈是调用次数不是引擎本身：RapidOCR（onnxruntime PP-OCRv4 mobile）已是中文 OCR 里最快的之一，全图 read_lines 1.9s。逐区域调用 ×40 次 = 40s；一次全图 + bbox 匹配 = 1.9s。本质是"循环搬到 GPU 外"问题改成"搬到 GPU 内一次跑"。
- 共享 reader 是自然结果：一帧只 OCR 一次全图，classify+parse 都走同一个 `RegionOcrReader`（其 `_lines` 缓存）。classify_by_ocr 内两遍（fast+full）也走同一 reader 缓存。
- bbox 中心点匹配：文字行的 bbox 四个角中心落在 region rect 内即该区域文字。简单、快、对布局变化鲁棒（不同于 absolute crop，不依赖区域精确像素对齐）。
- `isinstance(ocr_or_reader, RegionOcrReader)` 向后兼容：测试传 `OcrEngine`（仍可单独创建内部 reader，行为等价），live_loop 传 `reader` 共享。
- 实跑验证：单帧 ~2.4s（classify 2.88s + parse 0s），一轮训练（5-8 帧）≈12-20s **低于 30s 目标**；bot 真实完成 training_select→post_training；137 测试全过。
- 非纯迁移（性能优化 + 架构调整），旧 `逐区域 OCR` → 新 `全图批量化 + reader 共享`。

**§13 补充（2026-07-04 实机 GPU 再验证，见变更记录 §22.18）**：
- onnxruntime-gpu 1.27 在镜像源不可用，改用 1.23.2（要 CUDA 12 + cuDNN 9，非 CUDA 13）。
- CUDA 12 依赖链：nvidia-cublas-cu12 + nvidia-cudnn-cu12 + nvidia-cuda-runtime-cu12（cudart64_12.dll，关键缺失项，系统原仅 CUDA 11.7）+ nvidia-cufft-cu12 + nvidia-curand-cu12 + nvidia-cuda-nvrtc-cu12 + nvidia-nvjitlink-cu12。
- ocr.py PATH 注入 bug 修复：nvidia.* 是 PEP 420 命名空间包，`__file__` 为 None（原 `os.path.dirname(_m.__file__)` 抛异常被 except 吞掉 → DLL bin 未入 PATH → CPU fallback）。改用 `list(_m.__path__)[0]`；注入循环补 `nvidia.cuda_runtime`/`nvidia.cuda_nvrtc`/`nvidia.nvjitlink`。
- 验证：RapidOcrEngine(engine='gpu') 无 CPU fallback warning；OCR 0.59s/帧（vs CPU ~7s，~12x）；RTX 5060 Ti。

## §14 裁剪头像不含进度条 + 新库命名 N.png + NMS 修复
**背景**：旧裁剪窗口 113px 高含头像下方 ~20px 羁绊进度条。每次训练完成后，当前训练包含的人头增长羁绊值，进度条填充变化 → 模板 matchTemplate 分数下降到 0.85 阈值以下 → 漏识别 → 早期游戏训练决策错误（选错训练卡）。
**方案**：
- 新库命名 `N.png`（纯数字，如 `1.png`/`2.png`），与旧库 `counting_head_*.png`/`non_counting_head_*.png` 隔离。`collect_head_templates.py` 新增 `_is_new_library_template(path)` 判断 `^\d+\.png$`；模板预读/去重/命名全走新库。
- 裁剪高度 `_HEAD_H_FRAC = 93/260`（原 `113/260`），裁剪尺寸 111×93（排除底部进度条，保留头像圆形完整）。
- `vision.count_heads` glob 改 `*.png` + `_is_head_template` 过滤，仅用新库模板；旧库保留为遗留不动。
- `_find_head_instances` NMS 修复：
  - 原 NMS 按"相邻窗口 y 差 < 60 合并"，但滑窗步长 5 < 60 → 整列合并成 1 组（Bug）。
  - 改用 `loc_score` 局部极大值：`loc_score` = 所有模板（旧库+新库）最大匹配分，用于定位；在曲线上找局部峰值（score 比前后都高且 > 0.3），相邻峰值 y 差 ≤ 60 时保留更高分的。
  - 双分数：`loc_score`（含旧库，定位）+ `dedup_score`（仅新库，去重）。加载旧库做定位是因为新库初期模板少，无法定位所有头像；旧库含进度条但 matchTemplate 仍能定位（分数 0.5-0.9）。
  - 扫描范围扩大：`y_end` 从 `panel.y+panel.h-win_h` 改为 `image.h-win_h`（头像可能超出 panel 底部）。
**理由**：
- 进度条是动态变化的（随羁绊值填充），含进模板会导致模板随游戏进程漂移；只裁头像圆形区域（不含进度条）才能让模板稳定。
- 新库纯数字命名与旧库前缀命名隔离，避免混淆；旧库保留为遗留不删除（历史/备份）。
- NMS 局部极大值法比"相邻 y 差合并"更鲁棒：不依赖 std 曲线有明显的空槽低谷（实际画面整个面板 std 都 80+，无低谷），而是利用 matchTemplate 分数曲线的峰值定位头像。
- 双分数（loc/dedup）解耦定位与去重：定位可用旧库（含进度条但足以定位），去重只比新库（避免旧库进度条干扰去重判断）。
- 实机验证：修复后正确发现 3 个头像（y=155/260/370，间距 ~110px），采集入新库 `2.png`/`3.png`/`4.png`；`count_heads` 正确返回 3；137 测试全过。
- 非纯迁移（裁剪几何 + 命名约定 + NMS 逻辑全部改动）。

## §16 委托选择规则更新：+3 buffer 上限 + 全超退一阶
**背景**：用户实机场景 rank 22 + 三委托 rank 17/19/24，原 `decide_commission` 上限 = `character_rank`（22），doable = {17, 19}，取最高 = 19。但用户规则：「rank 22 最高能打 rank 25（超自己 3 级），大于 25 才退一阶」——rank 24 ≤ 25 可打，应选 rank 24 而非 19。原逻辑漏掉 rank 24（24 > 22 被过滤）。

**方案**：
- 新增 class 常量 `COMMISSION_RANK_BUFFER = 3`（`RelicCommissionMixin` 上）。
- `decide_commission` rank 比较分支：`limit = state.character_rank + COMMISSION_RANK_BUFFER`，doable = `[opt for opt in options if parse_first_int(opt.rank) ≤ limit]`，`best = max(doable)` 取最高。
- **退一阶分支**：doable 为空（全部委托 rank > limit，高阶讨伐太硬）→ 取所有委托里次高 rank 的（`sorted(reverse=True)` 取 `[1]`）。降一档比无脑选最低阶更合理：仍尽量挑战能打的高阶。
- **红字优先级不变**：`has_red_text=True` 仍优先于 rank 比较（红字 = 游戏标记的"适合当前角色"委托），不进 buffer 规则。

**理由**：
- +3 buffer 来自用户规则：rank 22 时最高能打 rank 25（用户实机经验，超自己 rank 3 级以内可打）。原 `≤ character_rank` 假设"超自己 rank 即不可打"过于保守，会漏掉合法高阶讨伐。
- 退一阶而非选最低：所有委托都超 limit 时（如 rank 22 + 26/28/30），退一阶取 28 而非最低 26——仍挑战能打的高阶，避免每次都打最低阶的低阶委托浪费时间。
- 红字优先于 buffer：红字是游戏 UI 主动提示的"适合"标记，比 rank 数字更可靠（游戏内部已综合判断），始终优先。
- 非纯迁移（决策规则改动），但 `decide_commission` 接口/`CommissionChoice` 模型不变，调用方零感知。

**实机验证**：
- rank 22 + 三委托 rank 17/19/24（无红字）→ limit=25，doable={17,19,24}，max=24 → 选 rank 24 ✓（原逻辑选 19）。
- rank 22 + 三委托 rank 26/28/30 全超 25 → 退一阶取 28 ✓。
- 红字优先：rank 17 红字 + rank 24 非红字 → 选 17（红字优先于 buffer 规则）。
- 端到端 5 帧：TRAINING_HUB 红字 banner → 点 commission_button → COMMISSION_SELECT 选 rank 24 → COMMISSION_SELECT 同帧确认 accept → BATTLE 开战点 skip → BATTLE 结束点 confirm。每帧 action 符合预期。
- 142 测试全过（137→142，+5 新增）。
- 非纯迁移（决策规则改动）。

## §17 奖励模板库（relics.json）+ 角色类型属性优先级 + 自动入库
**背景**：实跑发现 relic_choice 画面卡死 pause，原因：旧 `decide_relic` 按数字 score 比大小选卡（旧 UI 有分数），但当前画面已改为效果文本（如「自身的最大生命力增加4%」）→ score=None → pause。`relic_choice_card_N_description` 区域配置早就存在但 parser 没读。

**方案**：
- **模板库**：新建 `config/relics.json`（schema=v1），结构类似 `events.json`——纯文本数据不存图像。每条：`{name, effect_text, attributes}`。
- **新模块 `starsavior_trainer/relic_db.py`**：
  - `load_relics(path)` → list[RelicEntry]，文件缺失/损坏返回空 list。
  - `find_relic(relics, name)` → RelicEntry | None，精确名字匹配。
  - `save_relic(path, name, effect_text, attributes=None)` → upsert 入库（同名更新 effect_text/attributes，否则追加）。attributes 为 None 时自动 `extract_attributes`。
  - `extract_attributes(effect_text)` → tuple[str, ...]，按关键词表解析（顺序敏感：crit_rate 先于 crit_dmg 避免前缀吞）。OCR 偶在中文词中插空格（如「生 命力」）→ 匹配前去所有空白兜底。
  - `class_to_priority_group(cls)` → "attack" / "defense"。
  - `score_relic_by_priority(attributes, group)` → int（第 1 位=100，第 2 位=90，依此类推；无属性=0）。
- **角色类型 → 优先级组**（用户规则：游侠=弓手、突击者=战士，与刺客同组）：
  - ATTACK 组（输出系）：刺客/术师/游侠/突击者 → 优先级 speed > crit_rate > crit_dmg > attack。
  - DEFENSE 组（生存系）：辅助/坦克 → 优先级 speed > hp > defense。
  - 未知/None 默认 ATTACK（与原 decide_relic 一致，向前兼容）。
- **parse_relic_choice**：新增读 `relic_choice_card_N_description` → `effect_text`，调 `extract_attributes` → `RelicOption.attributes`。option 进入条件加 `effect_text` 非空（兼容旧画面 effect_text 全空时仍按 name/score 入 option）。
- **decide_relic 重写**：加载模板库 → 对每个 option 查表（find_relic）填 attributes；未匹配且有 effect_text → `save_relic` 自动入库；按 `class_to_priority_group(state.character_class)` 选优先级 → `score_relic_by_priority` 打分 → 排序选最高。同 priority 取 score_num 高；同 score 取 idx 小（更靠左）。score 数字作同优先级二次排序（兼容旧 score 画面）。
- **GameState 加 character_class**：`live_loop` 启动时按 `desired_character` 查 `config/characters.json` 填入（含 variant 匹配）。None → decide_relic 默认 ATTACK 组。
- **TrainerPolicy 加 relic_db_path 参数**：默认 `config/relics.json`，测试可注入临时文件（避免污染真实库）。

**理由**：
- 模板库（存名字+效果文本）而非模板匹配（存图像）——奖励不像支援卡头像是固定几何裁剪，而是文字内容；OCR 出文字直接查表比 matchTemplate 更准更快（无几何漂移问题）。结构沿用 events.json 已验证模式。
- 自动入库（不 dry-run 人工确认）：与人头模板库一致（自动采集）。OCR 偶发乱码时入库"无属性"垃圾记录，下次正常识别时 upsert 覆盖（save_relic 已实现 upsert）。

- 优先级组而非"按属性数字大小选"：奖励效果文本的数字（如 +4%/+6%）受百分比基数影响，不能直接比大小（如 5% 速度 vs 10% 攻击力，速度永远更优）。按优先级组选最高属性是用户指定的硬规则。
- 性能：查表 O(1)，extract_attributes 纳秒级，OCR 已被 RegionOcrReader 缓存复用（一帧一次全图 OCR），decide_relic 增量 <1ms。

## §18 OCR 引擎可配置（gpu/cpu/auto） + interval 默认 0.5s
**背景**：用户要求保留 onnxruntime（不卸载），加配置让用户自选 OCR 引擎；interval 3s 太慢，要 0.5s。

**方案**：
- `RapidOcrEngine.__init__` 加 `engine` 参数："auto"（默认，优先 GPU 回退 CPU）/"gpu"（强制 GPU，失败回退 CPU）/ "cpu"（强制 CPU）。`use_cuda` 旧参数保留兼容（True→"gpu", False→"cpu"）。
- `_is_cuda_active()` 间接检测：`onnxruntime.get_available_providers()` 含 `CUDAExecutionProvider` 即视为可用。rapidocr_onnxruntime 内部封装了 onnxruntime Session 无法直接拿 provider，用全局 get_available_providers 是可靠近似。
- engine=auto/gpu 但 CUDA EP 不可用时发 RuntimeWarning（不报错回退 CPU）。
- `cli/live_loop.py` 加 `--ocr-engine {auto,gpu,cpu}` CLI 参数（默认 auto）。
- `--interval` 默认 3.0 → 0.5s。

**理由**：
- 不卸载 onnxruntime（用户要求）：onnxruntime 和 onnxruntime-gpu 同时装时，`import onnxruntime` 加载的可能是 CPU 版本（providers 只返回 CPUExecutionProvider）。engine=auto 自动检测并回退 CPU，用户不需要手动卸载。
- engine="cpu" 强制 CPU：用户显式选 CPU 时不再尝试 GPU（避免 GPU 构造失败的 try/except 开销）。
- interval 0.5s：live_loop 是同步架构——一帧 OCR + 决策 + 执行完才下一帧，interval 只是帧间等待。0.5s 对回合制游戏（3-5s 一帧）完全够。总延迟 = OCR (CPU 2s / GPU 0.6s) + interval (0.5s) + 决策 (<1ms)。
- 保留 `use_paddle` 旧 flag 名兼容 web UI（实际走 RapidOCR）。
- 非纯迁移（新功能 + 参数变更），但 RapidOcrEngine 接口契约不变（OcrEngine Protocol：read_text/read_lines）。

## §19 商品模板库（shop_items.json）+ 角色类型分类匹配 + 多件购买
**背景**：旧 ShopInspector 按 `shop_buy_effect_keywords`（回体力/潜质点退还）关键词匹配买第一件，限购 1 件即退。用户需求：
- 商品库（类似 relic_db）：name + effect + price + classes + priority
- classes 按角色类型分可多选（一件商品可同时是游侠+刺客+坦克）；空=适合所有角色
- priority 0-5（数字越小越优先，用户手填）；自动入库默认 99（用户手填前不买）
- 按角色类型选符合的 + priority 升序逐个买（可买多件，不再限购 1 件）
- 界面商品分类只剩下不匹配角色类型时停止购买退出

**方案**：
- **模板库**：`config/shop_items.json` schema=v1，每条 `{name, effect, price, classes, priority}`。
- **shop_db.py 新模块**：
  - `MAX_BUY_PRIORITY = 5`（priority ≤ 5 才买，0=最优先 5=最低）
  - `DEFAULT_AUTO_PRIORITY = 99`（自动入库默认值，用户手填前不买）
  - `load_shop(path)` → list[ShopItemEntry]
  - `find_shop(items, name)` → ShopItemEntry | None
  - `save_shop(path, name, effect, price, classes, priority)` → upsert（同名保留 priority 不覆盖用户手填值）
  - `class_matches(item_classes, character_class)` → 空分类=True；多分类任一命中=True；无角色类型时空分类才=True
  - `should_buy(item, character_class, bought_effects)` → class_matches + priority ≤ 5 + 未买过 三条都满足
  - `filter_buyable(items, character_class, bought_effects)` → 按 priority 升序排序的可买商品
- **ShopInspector 重写**：
  1. 检视所有行（点击每行读 effect，保持原 inspect 流程）+ 同时记录 name/price
  2. 检视完查模板库（未入库的自动 save_shop priority=99）
  3. 按 `filter_buyable(character_class)` 排序，第一个未买的 → select 这行
  4. 下一帧 last_selected_index == target_idx → 点 buy_button（买完不清 effects，继续买下一件）
  5. 无可买的 → 点 back_button 退出 + policy._dday_trading_done=True
- **角色类型来自**：`policy.state.character_class`（live_loop 启动时按 desired_character 查 characters.json 填入；与 relic_db 共用）。

**理由**：
- 模板库（存名字+效果+分类+priority）而非关键词匹配——用户需求是按角色类型选商品，关键词匹配无法表达"游侠不要坦克装备"这种语义。模板库的 classes 字段直接表达角色类型分类。
- priority 0-5 而非 0-100：用户手填，5 档足够区分优先级；99 是哨兵值（自动入库默认，明确表示"未手填"）。
- save_shop upsert 保留 priority：用户手填 priority=0 后，再次自动入库（同一商品下次见到）不应覆盖。effect/price/classes 仍更新（OCR 可能更准）。
- 多件购买而非限购 1 件：用户明确要求买多件；每次仍需两步确认（select→buy）是 UI 强制（商品选中后才能买）。
- 角色不匹配时退出：避免无意义停留。用户场景"界面只剩坦克/辅助，角色是游侠 → 退出"由 `filter_buyable` 返回空 list 触发 step 5。
- 非纯迁移（新功能：模板库 + 多件购买 + 角色类型匹配），但 ShopInspector.decide 接口契约不变（接收 ShopScene + policy 返回 Action）。

## §20 ShopInspector 默认打开首个跳过点击 #1 + 详情面板刷新等待 + NEVER_BUY_PRIORITY
**背景**：实跑暴露 3 个问题：
1. **默认打开首个商品**：进入交易界面后游戏默认打开第一个商品的详细面板（selected_effect 非空）。此时再点击第一个商品会**关闭**详细面板（与点击其他行相反——其他行是打开）。旧 inspector 仍按 idx=1 点击 → 关闭面板 → 下一帧 selected_effect 空 → 误判 #1 未读到 → 卡死或重复点击。
2. **详情面板未刷新**：live_loop interval=0.5s 太快，点击 #X 后下一帧 OCR 时游戏详情面板还没刷新 → OCR 仍读到上一个商品的 effect → 全部商品 effect 都被录入成 #1 的（用户反馈"全部录入的商品1的详细，商品1的详细录入后需要点商品2才会出现商品2的详细"）。
3. **priority 99 语义模糊**：原 `DEFAULT_AUTO_PRIORITY = 99` 但 99 的语义不明确（是"永不买"还是"未手填"？）。用户要求明确："优先度加个分类，99代表绝对不买"。

**方案**：
- **step 1.5 默认打开首个跳过点击 #1**（[shop_inspector.py:67-75](file:///d:/starsavior-trainer-v2/starsavior_trainer/inspectors/shop_inspector.py#L67-L75)）：首次进入交易界面（`not self.effects and self.pending_index is None and scene.selected_effect.strip()`）时直接把当前 selected_effect 当作 #1 的 effect 记录（self.effects[1] = selected_effect），同时记录 self.names[1] = items[0].name / self.prices[1] = items[0].price，跳过点击 idx=1，从 idx=2 开始检视。条件 `not self.effects` 确保只在 effects 完全空时触发（reset 后再次进入也满足）。
- **step 1 等待详情面板刷新**（[shop_inspector.py:54-65](file:///d:/starsavior-trainer-v2/starsavior_trainer/inspectors/shop_inspector.py#L54-L65)）：新增 `last_seen_effect: str` + `settle_wait: int` 字段。step 1 检查 `new_effect == last_seen_effect`（与上次记录的 effect 相同）且 `settle_wait < 3` 时 return `Action("skip", None, "wait for shop item #X detail to refresh")` 等待刷新；`settle_wait` 递增到 3 时强制记录（避免真相同 effect 的商品死循环）。成功记录后 `settle_wait = 0`、`last_seen_effect = new_effect`。
- **NEVER_BUY_PRIORITY 常量**（[shop_db.py:42-47](file:///d:/starsavior-trainer-v2/starsavior_trainer/shop_db.py#L42-L47)）：新增 `NEVER_BUY_PRIORITY = 99`，`DEFAULT_AUTO_PRIORITY = NEVER_BUY_PRIORITY`。文档明确三档：
  - 0-5 = 会买（0 最优先，5 最低）
  - 6-98 = 低优先级不买（用户标记"暂不买"但区别于永不买）
  - 99 = 永不买（绝对不买；自动入库默认也是 99，用户手填前不买）
- **shop handler ocr_prefixes 扩展**：`screens/__init__.py` shop handler 的 ocr_prefixes 从 `["shop_detail"]` 改为 `["shop_item", "shop_detail", "shop_buy", "shop_back"]`，让 inspector 能读到商品列表 name/price（shop_item_N_name/price）+ buy/back 按钮坐标（shop_buy_button/shop_back_button）。

**理由**：
- **step 1.5 跳过点击 #1**：游戏 UI 行为差异（点 #1 关闭、点其他行打开）是游戏机制，不能改。inspector 必须感知"首次进入已默认打开 #1"这个状态，直接利用当前 selected_effect 当 #1 的 effect 而非点击。条件 `not self.effects` 保证只在首次进入触发，再次进入（reset 后）也满足。
- **等待详情面板刷新**：live_loop 0.5s 间隔对回合制游戏够快，但游戏 UI 渲染需要 1-2 帧才能刷新详情面板。OCR 读到旧 effect 是时序问题，不是 OCR 错误。等待逻辑（最多 3 帧 = 1.5s）让游戏有时间刷新；3 帧强制记录避免真相同 effect 的商品（如两件都"体力+3"）死循环。
- **NEVER_BUY_PRIORITY 语义明确化**：99 既是"永不买"也是"自动入库默认"，两者语义一致（用户手填前不买 = 永不买的默认状态）。新增常量让代码意图清晰（`DEFAULT_AUTO_PRIORITY = NEVER_BUY_PRIORITY` 比 `= 99` 更自解释）。6-98 中间档让用户标记"暂不买但可能以后买"区别于"永不买"。
- **ocr_prefixes 扩展**：原 `["shop_detail"]` 只读详情面板 effect，inspector 无法拿到商品列表 name/price 和 buy/back 按钮坐标。扩展后 inspector 能完整决策（检视 + 购买 + 退出）。
- 非纯迁移（行为修复 + 语义明确化），但 ShopInspector.decide 接口契约不变。
- 196 测试全过（188→196，+8 新增：等待逻辑 2 + D-DAY 5 + 其他 1）。

**实机验证**：
- iter 1: effects={1:'体力4增加'} pending=2，点击 #2
- iter 2: effects={1:'体力4增加', 2:'专注训练经验值增加'} pending=3，点击 #3 ✓（#2 effect 正确不同于 #1，等待逻辑有效）

## §21 D-DAY 评鉴战循环修复（_dday_rating_done 标志）
**背景**：D-DAY 评鉴战日大厅布局变成「评鉴战」+「交易」两个按钮（替代 normal hub 的训练/委托/休息三按钮）。原逻辑（§19 引入 `_dday_trading_done`）：先交易（`_dday_trading_done=True`）→ 再点评鉴战按钮 → 评鉴战 → 返回大厅。但评鉴战打完后返回大厅，`rating_battle_button` OCR 仍命中"评鉴战"文字（按钮可能未刷新或 OCR 误判）→ `_decide_training_hub` 又点评鉴战 → 死循环。

**方案**：
- TrainerPolicy 新增 `_dday_rating_done: bool = False` 标志（与 `_dday_trading_done` 并列，[policy/engine.py](file:///d:/starsavior-trainer-v2/starsavior_trainer/policy/engine.py)）。
- `_decide_training_hub`（[screens/__init__.py](file:///d:/starsavior-trainer-v2/starsavior_trainer/screens/__init__.py)）D-DAY 分支逻辑：
  - `rating_battle_button is not None`（检测到 D-DAY）时：
    - `not _dday_rating_done` → 走 D-DAY 流程（先交易再评鉴战，点过评鉴战后设 `_dday_rating_done=True`）
    - `_dday_rating_done=True` → fall through 走正常 hub 流程（点 training_button），不再点评鉴战
  - `rating_battle_button is None`（非 D-DAY）→ 清两个标志（`_dday_trading_done=False` + `_dday_rating_done=False`），下次 D-DAY 重新走流程

- `_dday_trading_done` 只能防交易重复点，不能防评鉴战重复点。评鉴战打完后按钮可能未消失（OCR 仍命中文字），需要独立标志 `_dday_rating_done` 防止反复点击。

- 非 D-DAY 时清标志：保证下次 D-DAY 日（rating_battle_button 再次出现）时两个标志都是 False，重新走"先交易再评鉴战"流程。
- 非纯迁移（新功能 + bug 修复），但 `_decide_training_hub` 接口契约不变。

### §22.4 训练失败率随训练值 gain 线性放宽 — 训练决策模型
- **核心关系**（用户设计 + 数学模型化）：训练成功 = +gain 属性；失败 = 0 训练值 + 降心情（心情影响训练加成，但可休息恢复）。所以**训练值越高，成功的收益越大于失败的代价，越值得冒高失败率**；普通训练（低 gain）失败代价相对收益高，应保守。
- **模型**：失败率上限 `max_fail = min(99, fail_rate_base + fail_rate_slope × gain)`（线性，[config.py](file:///d:/starsavior-trainer-v2/starsavior_trainer/policy/config.py) `fail_rate_base=10` + `fail_rate_slope=0.5`）。
  - 校准（实测 `_max_fail_for_gain`）：gain=0→10%、20→20%（普通保守上限）、30→25%、50→35%、60→40%、100→60%、150→85%、188→99%（cap）、200→99%。
  - 用户数据点 50→35%、60→40% 确认斜率 0.5%/gain；200 gain 99% fail 可赌 → cap 99%。
- **决策流程**（TRAINING_SELECT，**先看训练值才判断休息**——用户强调，符合当前架构 HUB→SELECT→decide_training→_needs_rest）：
  1. 每张训练卡读 gain + fail_rate。
  2. `fail_rate ≤ max_fail(gain)` → 可训；否则不可训。
  3. 有可训卡 → 选 `training_score` 最高的训练。
  4. 全不可训（失败率都超阈值，常因耐力低推高失败率）→ `_needs_rest` → 回 HUB → REST_SUBMENU（§22.3）。
- **实现**：[engine.py](file:///d:/starsavior-trainer-v2/starsavior_trainer/policy/engine.py) `_max_fail_for_gain(gain) = min(99, round(base + slope×gain))` 在 `training_score` 替换固定阈值（fail_rate > max_fail → -inf）。早期游戏 inspector 仍用固定 `max_training_fail_rate=30`。
- **衔接**：缺口2 blue 分支不受影响（blue fail_rate=None 走 blue 降级，不进 training_score）。缺口1 endurance 间接参与（耐力低→失败率高→超 max_fail→触发休息→REST_SUBMENU 按 §22.3 选冥想/露宿/住处）。

### §22.8 ShopInspector 检视顺序改 2→3→...→N→1（消除首商品 effect 错配）

**背景**：`RoundTracker` 靠大厅日期字符串变化计数回合（"3月下旬"→"4月上旬"=+1），不准：

- **OCR 跳帧**：OCR 偶尔丢月份数字（"月下旬"无月号）→ `_canonical_date` 返回 None → 不前进（坑 #29 保守设计，但导致计数漂移）。

用户需求：点大厅左上角"目标"二字 → 弹窗显示 `N/45`（绝对回合数，45=旅途总回合）→ 用 N 替代日期计数，让固定流程（第15回合地区移动→阿卡农、特定回合交易/评鉴战等）能稳定按回合数触发，避免误识别。

**目标弹窗结构**（实机 OCR 确认，bbox=[x1,y1,x2,y2]，region JSON 用 [x,y,w,h]）：
- 标题"旅程信息" (563,312,716,357) → `[563,312,153,45]` 锚点
- X 关闭按钮 (2005,313,2047,354) → `[2005,313,42,41]`
- "21/45" 回合数 (870,1027,953,1063) → `[870,1027,83,36]`
- 入口"目标"按钮（大厅左上"距离目标"区域，点 ~(276,81) 弹窗）→ `[246,61,60,40]`

**方案（注册表驱动 + 主动触发）**：
- **新画面 Screen.GOAL_DIALOG**（priority=2，参考 GAME_MENU/REWARD 弹窗模式）：
  - 分类签名 `_has_goal_dialog_signature`：`goal_dialog_anchor_title` 含"旅程信息"。这是弹窗独有标题，与背景大厅"距离目标"消歧。
  - parser `parse_goal_dialog`：读 `goal_dialog_round_label`("21/45") → `parse_first_int` 拿 N（"/" 自动断开数字 token，无需 split）。
  - 决策 `_decide_goal_dialog`：点 `close_button` 关闭回大厅。
- **入口（主动点目标按钮）**：`_decide_training_hub` 加分支——`_needs_goal_round` 标志 True 时优先点 `goal_button`。下帧 classify 到 GOAL_DIALOG → 读 N/45 → 点 X 关 → 回大厅。
- **回合数写回**：GOAL_DIALOG 时 `round_tracker.set_round(payload.round)`——N/45 绝对值覆盖日期计数。保留 `observe_date` 作 fallback（弹窗没读到时仍能靠日期计数兜底）。
- **触发时机**（避免每帧点弹窗干扰）：
  - 旅程首次进大厅（INITIAL/CHARACTER_SELECT reset 后）→ `_needs_goal_round=True` 必读
  - RoundTracker 检测到日期变化（回合+1）→ `_needs_goal_round=True` 校准
  - 不每帧点（干扰大）；日期变化是天然的"该校准了"信号。

**理由**：
- **新画面分类 > 内联读取**：符合架构契约（OCR 只产 Observation，状态机调度）。GOAL_DIALOG 作为独立 Screen，parser 读 N/45 产 Observation，policy 决策关闭，live_loop 在状态机外写回 state（同 rank_label 模式）。不绕状态机。
- **priority=2 关键**：弹窗背景是大厅，大厅 HUD（"距离目标"/"训练"/"委托"等）在弹窗下仍可见。若 priority 晚（如 TRAINING_HUB 的 8），分类器会先命中大厅文字 → 弹窗被抢走。priority=2 早检查（同 GAME_MENU/REWARD）。
- **set_round 覆盖而非并行字段**：N/45 是绝对回合数，比日期计数准。直接覆盖 `round_tracker._round`，下游 `state.current_round` 自动用校准值。不新建 `goal_round` 字段避免两套回合数语义混乱。
- **日期变化触发校准**：首次拿绝对值后，后续靠日期计数增量。但日期计数会漂移 → 每次日期变化时再校准一次，防止长期漂移。不每帧点（点弹窗是副作用，每帧点干扰大且 hub 决策要延迟帧）。
- **入口用 goal_button 而非硬编码坐标**：goal_button region 化，分辨率变化时随 profile 缩放，且可在 region JSON 调整。

**真机端到端验证**：
```
帧1: training_hub  current_round=1(日期计数)  action=点目标按钮
帧2: goal_dialog   N/45=21 → set_round(21)   action=点✕关闭
帧3: training_hub  current_round=21(校准值)   action=进训练(✨闪光)
```
- 弹窗分类置信度 1.0 ✓；大厅图（无弹窗）不误判为 GOAL_DIALOG ✓（识别为 TRAINING_SELECT）。
- current_round 从日期计数的 1 校准为 21，与游戏实际回合一致 ✓。

**测试**：`tests/test_goal_dialog.py` 15 个（parser 5：N/45 解析/锚点未命中 None/region 缺失/OCR 失败 round=None/容错变体；签名 5：旅程信息/程信息/空/距离目标不误判/region 缺失；注册 5：在 HANDLERS/priority=2/anchor+parse/在 ANCHOR_HANDLERS/排在 TRAINING_HUB 前）。240 → 255 全过。

**非纯迁移**：新增画面分类（Screen + parser + signature + handler）+ 回合数读取机制（set_round + 触发逻辑）+ TrainingHubStatus 字段。

**后续任务**（本次不做）：地区移动固定流程映射（第15回合→阿卡农）、region_move 坐标重校准、多目的地选择。

### §22.10 商品 always_buy 必买规则（综合营养剂/普通牛奶：条件购买，能买就必买）
**背景**：综合营养剂（解除负面旅程状态）/ 普通牛奶（状态恢复）这类商品特殊——**只有满足条件时（购买按钮变蓝）才能买，能买就必买**。现有 priority 体系（priority≤5 才买）无法表达"条件触发必买"，且 priority=99 默认不买会让这些关键商品被跳过。

**方案（always_buy 标记 + 按钮颜色检测）**：
- `ShopItemEntry` 加 `always_buy: bool`。always_buy=True 的商品**无视 priority**（priority 保持 99 明确不走 priority 体系），只要"能买"（按钮蓝）就必买。
- **按钮颜色检测点**：inspector 检视商品时（effect 记录段，§22.8 的 2→3→1 顺序选中每行那帧），对 always_buy 商品调 `is_blue_region(scene.buy_button, image)`——蓝=能买→记入 `buyable_always`；灰=不能买→跳过。
- **最高优先购买**：决策时 `buyable_always` 优先于 `filter_buyable`（priority 体系）。即 always_buy 能买的商品先买完，再按 priority 买其它。

**理由**：
- **专门标记 vs priority=0**：priority 是"数字越小越优先"的通用排序；always_buy 是状态依赖的条件购买（按钮蓝才买），语义不同。混进 priority 会污染体系（priority=0 会无视条件总买，但综合营养剂无负面状态时不能买）。专门标记隔离两种语义。
- **按钮颜色检测在 inspector（决策层）**：颜色是"当前选中商品能否购买"的信号，依赖选中态，属于决策层不是 observation。parser 只读 OCR 文本。符合架构契约。
- **is_blue_region 复用**：现有 `vision.is_blue_region` 已用于多个画面（蓝按钮检测），直接复用。

**真机验证**：当前角色无负面状态 → 综合营养剂按钮灰（coverage=0.000）→ 不在 buyable_always → 走 priority 体系 → 术师无匹配退出。验证"灰色不买"路径正确（"蓝色必买"路径需有负面状态时验证，单测已覆盖）。

**测试**：shop_db 3（load/save/upsert 保留）+ inspector 4（蓝→买/灰→不买/最高优先于 priority=0/灰时回落 priority）。255 → 262 全过。

### §22.11 地区移动多目的地选择 + 回合数兜底（弗洛拉/卡莱德 按角色类型选）
**背景**：第二次地区移动（第30回合）有 2 个目的地，需按角色类型选：
- 弗洛拉：术士/游侠/突击者（力量+专注训练加成）
- 卡莱德：坦克/辅助（体力+保护训练加成）

第一次（第15回合，阿卡农）只有 1 个目的地（fallback 点 destination_1）。第15/30回合必定是地区移动——分类失败时用回合数兜底。

**方案**：
- **parser 结构化**：`parse_region_move` 从裸 `Rect` 改返回 `RegionMoveStatus(destinations, go_button, is_region_move)`。收集所有 `destination_N` + name region，让决策层能按 name 选。
- **决策按角色类型选**（`_decide_region_move`）：
  1. go_button 亮（已选目的地）→ 点前往
  2. 否则遍历 destinations，按 `state.character_class` 匹配 `region_destinations` 配置 → 选匹配的目的地
  3. 无匹配/角色未知/阿卡农（不在映射）→ fallback 点 destination_1
- **回合数兜底**（live_loop）：UNKNOWN + `current_round in region_move_rounds={15,30}` 时，尝试 `parse_region_move`——成功（is_region_move=True）则强制按 REGION_MOVE 决策，避免分类失败时误点中心推进错过地区移动。

**理由**：
- **parser 返回结构化 payload（breaking change）**：裸 Rect 无法支撑多目的地选择（决策层不知道有哪些目的地、各自叫什么）。结构化 payload 让决策层能按 name 匹配角色类型。
- **配置化映射（非硬编码）**：`region_destinations` 放 PolicyConfig，用户可调整（未来新目的地/角色类型映射只需改配置）。阿卡农不在映射→自然走 fallback。
- **回合兜底在决策层不在 classifier**：classifier 只看图像（OCR 只产 Observation 契约）。第15/30回合 UNKNOWN 时，live_loop 用回合数+region 信息兜底（同 §22.9 GOAL_DIALOG 回合校准模式）。
- **fallback 兜底第一次**：第一次阿卡农只有1个目的地，不在 region_destinations 映射→fallback 点 destination_1 已覆盖，无需专门处理。

**真机验证**（当前术师第30回合）：parse 出弗洛拉+卡莱德 2 目的地 → 决策"选 弗洛拉(术士 加成)"（destination_1, y=370）✓；回合兜底路径 parse_region_move is_region_move=True ✓。

**测试**：parser 3（2目的地解析/前往按钮/锚点未命中 None）+ 决策 8（术士→弗洛拉/坦克→卡莱德/游侠→弗洛拉/辅助→卡莱德/已选→前往/角色未知→fallback/阿卡农→fallback/无目的地→pause）。262 → 271 全过。

### §22.12 潜质模板库 skill_db + 潜质自动入库脚本（第一步：入库）
**背景**：旅程结束点"潜质"二字进入潜质学习窗口，需识别全部潜质入库模板库（战斗/种马两套优先级）。本次只做入库脚本，学习决策是第二步后续任务。

**潜质学习窗口结构**（实机 OCR 确认）：
- 每行潜质（行高 ~170px）：状态标签"未习得/已习得"(左 x≈1034) + 折扣标签"35%SALE"(x≈2006, y偏上) + 习得按钮"习得"(x≈1882, y居中) + **价格数字**(65/80 等, x≈2018-2091, y居中) + 潜质名(攻击感知/洞察星痕等, x≈1030, y偏下)
- 潜质点数(2857, 2124,1103) + X 关闭(2159,332) + scrollbar [2165,365,22,675]（可滑动，潜质不止4个）

**方案（两套优先级一库 + 状态标签锚点识别）**：
- **skill_db.py**（仿 relic_db）：`SkillEntry(name, effect, kind, battle_priority, breeding_priority)`。两套优先级存一个 JSON 避免重复维护潜质名；kind 按名尾字推断（感知/技巧/天赋/通用）用于识别原价类型。`load_skills`/`find_skill`/`save_skill`（upsert 保留手填 priority）。
- **collect_skills.py 入库脚本**：
  - **滑动扫库**：复用 `_drag_scroll` ctypes 实现，scrollbar 中心上滑（内容上移看下方），连续 2 次名字集合不变 = 到底。多帧累积按 name 去重。
  - **状态标签锚点识别**（关键）：每行潜质都有"未习得/已习得"标签 → 以此为锚点定位行，在同 y±60 找潜质名（左 x 1000-1800）+ 价格（右 x>1950 最右数字，避开 SALE）。**不依赖名字尾字**——能识别"洞察星痕"/"锐利攻势"等任意命名潜质，不只感知/技巧/天赋三类。
  - **价格多帧取最大值**：单帧 OCR 可能少读一位（8 vs 80），多帧累积取最大纠正。
  - 名字合理性校验：≥2 字且非纯 ASCII 单字符（过滤"q"误读）。

**识别逻辑演进**：初版按"感知/技巧/天赋"尾字识别行 → 漏掉非三类命名潜质（洞察星痕/锐利攻势/深红誓约等）。改为"未习得/已习得"状态标签锚点定位行后，覆盖所有潜质（实机扫到 16 个）。

**理由**：
- **两套优先级一库 > 两库**：避免重复维护潜质名（同一个潜质在战斗/种马两场景下优先级不同，但名字/effect/kind 相同）。运行前配置选决策时用 battle_priority 还是 breeding_priority（第二步实现）。
- **状态标签锚点 > 名字尾字**：游戏潜质命名多样（不只"xx感知"三类），状态标签是每行都有的固定结构特征，更可靠。
- **价格取最大值**：OCR 少读一位（8 vs 80）时，多帧看到 80 就取 80。入库价格仅参考（决策靠手填 priority），偶发误读可接受。

**实机验证**：扫到 16 个潜质（滑到底自动停）；清理 OCR 误读后入库 15 个（5 感知 + 2 技巧 + 2 天赋 + 6 通用含洞察星痕/锐利攻势/深红誓约/速度星痕/坚固的破坏/星光轨迹一EX5号）。

**测试**：`tests/test_skill_db.py` 14 个（infer_kind 4 + load/find/save 10 含 upsert/priority=0/priority 显式覆盖/优先级保留）。271 → 285 全过。

**后续任务**（第二步）：潜质学习决策（按优先级+折扣背包规划）、战斗/种马两模型切换、hub 入口分支、运行前配置、重校准 skill_select region JSON。

### §22.13 潜质学习决策核心（hub 入口 + 贪心学习 + SkillInspector）
**背景**：旅程结束（can_learn_skill + 潜质点数够）应进技能窗口学习潜质。需求：滑动扫库识别全部 → 贪心按优先级+折扣学习，**买到买不起为止**。本次只做战斗模型（battle_priority）。

- **共享 skill_reader**：避免 collect_skills 和 skill_inspector 重复 OCR 逻辑。状态标签锚点识别是核心（不依赖名字尾字，覆盖任意命名潜质）。

**干跑验证**：

- button 匹配：name_cy 589/763/936 → option_N_button dy 64-65 < 90 ✓
- skill_reader 读潜质行：锐利攻势/坚固的破坏/深红誓约 price=200 未习得 ✓

**待实机验证**：点习得后行为（假设下帧刷新不弹确认框）；端到端 live_loop 跑通（真消耗潜质点+真学习，需用户确认时机）。

**测试**：`tests/test_skill_learn.py` 10 个（priority 升序/同 priority 折扣降序/过滤已习得/priority 太高/买不起/无 target/next 返回/next None/原价表）。285 → 295 全过。

### §22.14 事件自动入库（live_loop 集成 + 默认点第1选项）
**背景**：事件库（events.json 22 事件 + event_db 读/匹配/选 option）已成熟，但缺自动入库——新事件需人工填。事件是旅途中随机出现的，不像技能/商品在固定画面可提前入库，独立脚本不现实。

**方案（decide_event 内自动入库 + 写规则选第1个）**：
- **event_db 加 save_event/find_event_exact/_clear_cache**（照 skill_db 模式）：
  - `find_event_exact(events, title)`：精确名查找（判"是否已入库"，不用模糊匹配）。
  - `save_event(title, options_text, choose_option=1)`：新事件入库，写 `default_rules:[{profile:"default",choose_option:1}]` + options 文本 + status:"auto_inserted"。已存在精确名→不覆盖（保留用户手填规则）。
  - `_clear_cache()`：save 后清 `_EVENT_DB_CACHE`（下次 _load_event_db 重读）。
- **decide_event 内自动入库**（`_event_db_choice`）：
  - `_match_event` 返回 None 且 `find_event_exact` 也 None（确认未入库）→ `save_event`(choose_option:1) → 清缓存重读 → 重新 `_match_event` 命中 → `_event_recommended_index` 返回 1 → 选 options[0]。
  - 未入库→入库+选第1个**在同一帧完成**，脚本继续运行。

**理由**：
- **集成到 decide_event 不写独立脚本**：事件随机出现，decide_event 是事件决策唯一入口，在此自动入库最自然（同 shop_inspector 自动入库商品）。独立脚本需要用户预知事件出现时机，不现实。
- **入库写规则而非改 fallback**：走第1级 db_choice（最干净，符合现有架构"决策优先用 db"），不污染第3级关键词 fallback（保留给已入库但无 profile 规则的事件）。
- **精确 find 不用模糊**：判"是否已入库"用精确名（`find_event_exact`），避免 `_match_event` 模糊匹配（阈值0.6）把相似事件误判为已入库而跳过自动入库。
- **save 不覆盖**：已入库事件保留用户手填规则（同 skill_db priority 语义），只入新事件。

**测试**：`tests/test_event_db.py` 8 个（find_event_exact 3 + save_event 3 含不覆盖/清缓存 + decide_event 自动入库+选第1个/已知事件用已有规则 2）。295 → 303 全过。

### §22.15 统一日志系统（配置文件控制 + debug_log 改 logging + 补 narrate）
**背景**：项目有两套割裂日志——`debug_log.py`(print-only, --debug 全有或全无, 不落盘, 仅 3 画面定制) + `logging_setup.py`(正式 logging 落盘+轮转+错误分离, 但无 per-logger 配置开关)。`narrate` 行为日志仅 7 处调用(live_loop 顶层)，policy/inspectors 层完全无日志，出问题难排查。

  - relic_commission：奖励自动入库 / 选最高分奖励 / 委托决策
  - event：事件自动入库

- **复用 logging_setup 基础设施**：不新建日志系统（基础设施已就绪——落盘+轮转+错误分离+UTF-8+10 模块在用），只加配置文件加载 + debug_log 改 logging。

- **默认全 INFO**：开箱不刷屏（原来 --debug 全开刷屏）。debug_log 默认 INFO（不输出每帧 dump），需要时改 config debug_log=DEBUG 或用 --debug。

### §22.17 卡死保护：同一画面停留超 30s 自动停止（用户需求）
**背景**：实跑中脚本可能卡在同一画面——inspector 死循环（OCR 抖动反复读同一值导致检视器无法推进）、决策死循环（CHARACTER_SELECT 已有局部防护但其它画面无全局兜底）、游戏弹窗未关闭导致 OCR 持续命中同一画面。无限占用游戏不安全（用户需强制杀进程才能 reclaim 控制权）。

**方案（画面停留计时 + 超时退出）**：
- live_loop 主循环加 `stuck_screen`/`stuck_since` 状态变量。每帧 classify 后：若 `observation.screen != stuck_screen`（画面变化）→ 重置 `stuck_screen` + `stuck_since=now`；若同一画面且 `now - stuck_since > --stuck-timeout` → 保存 `screenshots/live_stuck_latest.png` 截图 + 打印画面名+停留时长 + return 退出。
- 检测点在 `consecutive_unknown = 0` 之后、payload 解析之前。UNKNOWN 画面有独立 `consecutive_unknown` ≤4 帧点中心/>4 帧 pause 机制（坑 #17-19），不重复检测；UNKNOWN 兜底成 REGION_MOVE 的帧会经过卡死检测（正确，REGION_MOVE 需正常 parse/decide）。
- `--stuck-timeout` 默认 30s（`_STUCK_TIMEOUT` 常量），设 0 关闭。

**理由**：
- **30s 不误杀 inspector**：SHOP/TRAINING_SELECT/COMMISSION_SELECT/SKILL_SELECT 检视器多帧工作（逐个点击读 effect/heads/rank），interval=0.5s × ~10-20 帧 < 15s，远低于 30s。真卡死（OCR 抖动/决策死循环/游戏无响应）必超 30s。
- **画面变化即重置**：A→B→A 不算卡死（画面有切换=有进展）。只有持续停留同一 screen 才计时。
- **保存截图**：退出前存 `screenshots/live_stuck_latest.png`，供离线排查卡死根因（OCR 读了什么/决策选了什么）。
- **与 CHARACTER_SELECT 局部防护互补**：CHARACTER_SELECT 有"连续 3 次相同 click → pause"（action 级防护）；卡死保护是 screen 级全局兜底，覆盖所有画面。

**验证**：`import` OK + `_STUCK_TIMEOUT=30.0`；test_live_loop_helpers 2 测试过。卡死保护是 main() 控制流（依赖实机窗口/帧时序），离线单测归 T18 实跑范畴。

### §22.19 实机日志分析优化：训练检视器防重复检视 + 置信度阈值 + 循环节奏提速
**背景**：40 帧 `--execute` 实跑日志分析发现 3 类问题：(1) 训练检视器确认后画面未切走时重新检视，点击了 0 人头卡（用户报告 bug）；(2) blessing_choice 置信度 0.70 < 0.75 阈值 → pause 浪费帧；(3) sleep 参数偏保守拖慢节奏。

**方案**：
1. **训练检视器防重复检视**：TrainingInspector 加 `confirmed`/`head_confirmed` 标志。确认按钮点击后置 True（不清空 records/head_counts）→ 下一帧 `decide()`/`_decide_early_game()` 检测标志直接返回 None（不点任何卡）→ 画面切走后 live_loop 调 `reset()` 清除标志。非早期路径同理（`self.reset()` 改 `self.confirmed = True`）。
2. **置信度阈值 0.75→0.65**：`PolicyConfig.min_screen_confidence`。实机各画面置信度分布——training_hub 0.86、training_select 0.90、commission_select 1.00/0.75、blessing_choice 0.70、dialogue/reward/relic/battle 1.00、unknown 0.00。0.65-0.75 区间仅 blessing_choice（0.70），降低阈值让它通过。0.00（unknown）仍被拦。
3. **循环节奏提速**：`_ADVANCE_SLEEP` 0.35→0.25、`_TRAINING_SELECT_SLEEP` 0.5→0.35、`--interval` 0.5→0.3。OCR GPU 0.6s/帧是主要耗时，sleep 是次要耗时（40 帧约 20s sleep），缩短后约 12s。

**理由**：
- **confirmed 标志不依赖画面检测**：inspector 不感知画面切换，由 live_loop 的 `observation.screen != Screen.TRAINING_SELECT → reset()` 驱动清除。确认后同一帧再调 inspector 时 confirmed=True 拦住，等画面切走 reset 清除，下次进 TRAINING_SELECT 是新检视周期。
- **0.65 不误放 unknown**：unknown 置信度 0.00 < 0.65 仍被拦 pause。0.65 仅放行 blessing_choice（0.70），无其他画面落入此区间。
- **sleep 提速安全**：advance 画面（dialogue/reward）游戏动画 <0.2s，0.25s 足够；训练卡预览 0.3s 渲染完成，0.35s 足够；一般画面 0.3s 间隔不影响游戏响应。

**验证**：303 测试全过（test_policy_engine 期望值 0.75→0.65 同步更新）。

### §22.20 头像计数 Bug 修复：count_heads 位置 NMS + auto_collect 去重阈值对齐
**背景**：用户报告"明明只有一个人头，但头像模板库里有多个类似的图片就是识别为多个人头"。根因：去重阈值 0.93 > 识别阈值 0.85，[0.85, 0.93) 区间的"准重复"模板被 auto_collect 入库后，count_heads 用它们独立计数 → 同一头被计多次。

**方案**：
1. **count_heads 位置 NMS**（vision.py）：收集所有模板命中位置 (x, y, score) → 按分数降序 NMS（dy < `_HEAD_NMS_DY`=60px 只保留最高分）→ NMS 后的命中检查羁绊达标。即使模板库有同一颗头的多个相似模板，NMS 合并同位置命中 → count 正确。
2. **auto_collect 去重阈值 0.93→0.85**：去重灵敏度 = 识别灵敏度，消除准重复入库。同一颗头裁剪稍有偏差也判为重复（不入库）。

**理由**：
- **NMS 是根本修复**：即使模板库已污染（有重复模板），count 也正确。NMS 距离 60px < 头像间距 109px，不会误合并不同头像。
- **阈值对齐是预防修复**：从源头阻止准重复入库。0.85 = 识别阈值，去重灵敏度 ≥ 识别灵敏度，不会漏入库新头像（新头像与所有现有模板匹配 < 0.85 才入库）。
- **现有模板库无需清理**：6 个作数模板两两匹配最高 0.798 < 0.85，无重复。

**验证**：303 测试全过。
